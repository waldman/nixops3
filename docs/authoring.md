# Authoring Roles and Profiles

## The mental model

Think of it like Puppet's role/profile pattern:

- A **profile** is a reusable NixOS module that configures one concern (SSH, Docker, a specific service).
- A **role** is the composition: it imports the profiles a machine needs and sets role-level variables.
- A **host override** is a thin layer on top of the role for anything host-specific (hostname, IP, extra users).

The NixOS module system handles merging. You write declarative modules; NixOS figures out the right system state.

## Writing a profile

A profile is a standard NixOS module. It should configure exactly one concern and expose sensible defaults.

```nix
# profiles/docker.nix
{ pkgs, ... }:
{
  virtualisation.docker = {
    enable = true;
    autoPrune.enable = true;
  };

  environment.systemPackages = with pkgs; [ docker-compose ];
}
```

```nix
# profiles/base.nix
{ pkgs, ... }:
{
  environment.systemPackages = with pkgs; [
    curl
    git
    htop
    vim
  ];

  services.openssh = {
    enable = true;
    settings.PasswordAuthentication = false;
  };

  nix.settings.auto-optimise-store = true;
}
```

Keep profiles focused. A profile that configures both SSH and monitoring is harder to reuse than two separate profiles.

## Writing a role

A role imports the profiles it needs and sets role-level options. The key convention: use `<nixops3/...>` for profile imports so the daemon can discover and download them.

```nix
# roles/home/production/webserver/main.nix
{ config, pkgs, ... }:
{
  imports = [
    <nixops3/profiles/base.nix>
    <nixops3/profiles/nginx.nix>
    <nixops3/profiles/monitoring.nix>
  ];

  networking.hostName = "webserver";

  services.nginx = {
    virtualHosts."example.com" = {
      enableACME = true;
      forceSSL = true;
      root = "/var/www/example.com";
    };
  };
}
```

The daemon scans `main.nix` for `<nixops3/...>` patterns and downloads exactly those files from S3. Adding a new profile to the bucket has no effect until a role imports it.

## Writing a host override

A host override adds anything that differs between machines sharing the same role: the actual hostname, IP-specific config, per-machine users, or hardware quirks.

```nix
# roles/home/production/webserver/web-01.example.com/main.nix
{ ... }:
{
  networking.hostName = "web-01.example.com";

  # Host-specific SSH key for the ops user on this machine
  users.users.ops.openssh.authorizedKeys.keys = [
    "ssh-ed25519 AAAA... ops@laptop"
  ];
}
```

The host `main.nix` does not need to import the role — the daemon-generated `configuration.nix` imports both independently. Just add what differs.

## Generated configuration.nix

The daemon writes `/var/lib/nixops3/current/configuration.nix` before every rebuild. It always looks like:

```nix
# Generated by nixops3d — do not edit manually
{ ... }:
{
  imports = [
    /etc/nixos/hardware-configuration.nix
    ./roles/home/production/webserver/main.nix
    ./roles/home/production/webserver/web-01.example.com/main.nix
  ];
}
```

`hardware-configuration.nix` is always first. The host import is omitted when no host `main.nix` exists. Profiles are not listed here — they are imported by the role's own `main.nix` via `<nixops3/...>`.

## Using inventory data in .nix files

If inventory is enabled (see [Inventory](inventory.md)), the daemon writes `/var/lib/nixops3/inventory.json` before each rebuild. You can read it in any `.nix` file:

```nix
# profiles/zookeeper-client.nix
let
  inv = builtins.fromJSON (builtins.readFile /var/lib/nixops3/inventory.json);
  zkNodes = inv.queries.zookeeper_nodes;
in
{
  services.kafka.zookeeper.servers = map (n: n.ip) zkNodes;
}
```

`builtins.readFile` is evaluated at `nix eval` time during `nixos-rebuild`. Because the daemon writes `inventory.json` before calling `nixos-rebuild`, the data is always fresh for that cycle.

## Using secrets in .nix files

Secrets are written to `/run/nixops3/secrets/<name>` (tmpfs, mode `0400`) before each rebuild. The recommended pattern is `EnvironmentFile` in systemd service definitions — the secret is read at service start time, not at eval time, and never ends up in the Nix store:

```nix
# profiles/my-service.nix
{ ... }:
{
  systemd.services.my-service = {
    wantedBy = [ "multi-user.target" ];
    serviceConfig = {
      ExecStart = "${pkgs.my-service}/bin/my-service";
      EnvironmentFile = "/run/nixops3/secrets/my-service-api-key";
    };
  };
}
```

Avoid `builtins.readFile /run/nixops3/secrets/...` for sensitive values — that copies the secret into the Nix store, which is world-readable.

See [Secrets](secrets.md) for how secrets are provisioned.

## Override priorities

The NixOS module system evaluates all imported modules and merges them. When the same option is set in multiple places, the last-writer-wins rule applies unless you use `lib.mkDefault` or `lib.mkForce`.

Recommended pattern: profiles use `lib.mkDefault` for anything a role should be able to override:

```nix
# profiles/base.nix
{ lib, ... }:
{
  services.openssh.settings.PermitRootLogin = lib.mkDefault "no";
}
```

```nix
# roles/home/production/rescue/main.nix — can override the profile default
{ ... }:
{
  imports = [ <nixops3/profiles/base.nix> ];
  services.openssh.settings.PermitRootLogin = "yes";  # overrides mkDefault
}
```

## Naming conventions

| Thing | Convention | Example |
|-------|-----------|---------|
| Profile file | `snake_case.nix` | `default_packages.nix` |
| Role directory | `snake_case` | `generic_node`, `zookeeper` |
| Abstraction | lowercase, short | `home`, `aws-use1` |
| Environment | lowercase | `production`, `staging` |
| Hostname | FQDN | `web-01.example.com` |
